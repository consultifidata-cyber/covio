## 1. Data Persistence — Verdict: **PASS (design) / PARTIAL (capacity claim)**

**Where things live** (all re-verified by direct code reading this session):
- Raw pulse state: ESP32 PCNT hardware register (`totalizer.h:143-173`), volatile.
- Current totals: RAM (`base_`+`accumulated_`+live PCNT), checkpointed to LittleFS dual-slot `/totA.bin`/`/totB.bin` (`totalizer.h:27-28,228-239`).
- Per-sample readings: LittleFS segmented queue, `/queue/seg_NNNNNN.bin` (`queue.h:33,103,119-211`).
- Sequence numbers: RAM (`seq` global, `covio_firmware.ino:46`), embedded in every `QRow` and checkpoint, globally monotonic.
- Unsynced records: same segmented queue files — durable, not RAM-only.
- Ack state: LittleFS dual-slot `/queue/ackA.bin`/`ackB.bin` (`queue.h:34-35,469-479`).
- RAM-only: the live PCNT register value not yet drained, and the in-flight `QRow` being built each second before `append()` returns.
- Survives reset/brownout/power-loss: everything **except** the above RAM-only slice, by design (dual-slot CRC checkpoints + flush-before-return row writes).

**Record size, real not assumed:** `QRow` is `__attribute__((packed))`: `4+2+2+4+4+4+8+2+2+4 = 36 bytes` (`queue.h:51-62`) — confirmed by reading the struct, not a repeated claim.

**Capacity — the mandate's specific instruction ("do not accept `QUEUE_HIGHWATER` as the real capacity") was followed:**
- `QUEUE_HIGHWATER = 20000` (`config.h:93`) is confirmed, by reading `diagnostics.h:213-226`, to be a **soft alert threshold only** — exceeding it sets a `QUALITY_BACKLOG_HIGH`/`QUEUE_HIGH`/`QUEUE_CRITICAL` flag, it does **not** stop buffering or evict anything. This is PARTIAL, not FAIL — the design deliberately keeps accepting data past the threshold rather than dropping it, which is the safer failure direction, but it means the "capacity" a customer might read off that constant is not a hard limit.
- The real physical ceiling is the LittleFS partition size. `platformio.ini`/`config.h`'s own comments state ~3.4 MB for the "spiffs" slot on the `default_16MB.csv` table. **This audit did not independently open the literal `default_16MB.csv` partition CSV file** (it lives inside the PlatformIO package cache, not this repo) to confirm the byte-exact partition boundaries — this specific sub-claim is **NOT PROVEN**, sourced from a code comment, not a verified partition dump. The real compiled flash-usage figures (Flash: 15.6%/15.8% of "6553600 bytes" reported by `pio run`'s own size-check step, which reads the actual linked app-partition size) are real, though that number describes the **app** partition, not the separate LittleFS data partition — they are not directly interchangeable.
- At 36 bytes/row, `QUEUE_HIGHWATER=20000` ≈ 720 KB — comfortably under the claimed ~3.4 MB, leaving headroom the comment describes as "~5.5 hours at 1 row/sec." This arithmetic is verified; the partition-size input to it is not independently confirmed.
- **Buffering duration at other cadences:** at 1/sec (current `TELEMETRY_PERIOD_MS`), ~5.5h to the soft threshold as above; at 1/10sec, ~55h to the same soft threshold (linear scaling — the code has no cadence-dependent capacity logic); true physical exhaustion (assuming the ~3.4 MB figure holds) would occur at roughly 4.7x the soft-threshold point, i.e. ~26 hours at 1/sec or ~11 days at 1/10sec. These physical-limit figures inherit the same NOT PROVEN caveat on partition size.
- **Behavior at 80/90/95/100% of the *soft* threshold:** no distinct behavior at all — the only two states are "under 1000 unacked" (no flag), "1000-10000" (`QUEUE_HIGH` warning), ">10000" (`QUEUE_CRITICAL`) per `diagnostics.h:213-226`. There is no 80/90/95% staged behavior in code — **ABSENT**, not a hidden feature.
- **Behavior at true physical fullness:** `queue.h:137-138,183-206` — a failed segment open or short write is logged (`"segment append open FAILED"` / `"segment write SHORT"`) and the checkpoint is **not** advanced, so the row is effectively dropped for that cycle and retried never (there's no explicit retry of a specific failed append — the *next* telemetry tick just tries again with a *new* row; the failed one is gone). This is the one place this audit found where **data can be silently lost**: a write failure at true flash-full capacity does not raise any alarm distinct from a normal write, and the specific row that failed to write is not resent. This is a real, code-provable gap.

**Failed-write detectability:** partially — `queue.h` logs to Serial on a failed open/short write, and `sd_write_latency_ms` (`diagnostics.h:114`) is populated even on a failed attempt, but there is no counter or alarm surfaced via the local API distinguishing "one write failed" from normal operation — an operator watching only `/api/v1/status`/`/health` would not see it.

**Pulse accumulation continues on queue-write failure:** **yes** — `totalizer.h`'s PCNT hardware counting is entirely independent of `queue.h`'s flash writes; a failed `append()` does not affect the totalizer. Confirmed by code structure (they are separate classes with no shared failure path) and by the architecture's own explicit design comment ("Hardware counts, software ships").

**Severity: P1** (the silent-drop-on-flash-full case). **Blocks plant deployment: Yes**, until either (a) capacity is confirmed with a byte-exact partition read and shown to be adequate for the customer's real offline-duration requirement, or (b) the flash-full silent-drop path is fixed to at least surface a distinct alarm/counter.

## 2. Flash Memory Reliability — Verdict: **NOT PROVEN**

Every file/NVS key and its write frequency, confirmed by code:
| Data | Path | Write frequency |
|---|---|---|
| Telemetry rows | `/queue/seg_NNNNNN.bin` | Every `TELEMETRY_PERIOD_MS` (1s), append-only |
| Totalizer checkpoint | `/totA.bin`/`/totB.bin` alternating | Every `totalizer.service()` call = every 1s (`covio_firmware.ino:193`) |
| Ack cursor | `/queue/ackA.bin`/`ackB.bin` alternating | Only on a confirmed cumulative ack (`queue.h:409`) — i.e. up to once per `PUSH_PERIOD_MS` (5s), not every second |
| NVS (`server_url`,`api_key`,`wifi_*`,`cfg_ver`,`boot_id`,`logical_id`) | ESP-IDF NVS partition | Only on provisioning/config-poll-version-change events, not periodic |

**Append vs rewrite:** queue rows are pure append (`FILE_APPEND`). Checkpoints are full-slot rewrites (`FILE_WRITE`, which truncates+rewrites), but alternate between two slots (ping-pong), which is itself a form of wear-spreading across those two specific slots — **but the totalizer checkpoint rewrites a slot once per second, forever, for the life of the device.** That is a **hot sector** by definition: two fixed LittleFS files, each rewritten roughly every 2 seconds (alternating), continuously, for years.

**Erase-cycle math (assumptions stated explicitly):** LittleFS performs wear-leveling *within* a file's allocated blocks as it grows/shrinks, but a small, fixed-size file (`Checkpoint` is `4+8+4+4+4+4+4+4=36` bytes, well under one flash page) being rewritten every ~2 seconds forever will cycle through whatever blocks LittleFS's own internal wear-leveling allocates for that file — LittleFS is designed for exactly this (dynamic wear-leveling, not a raw filesystem), but **this audit has no visibility into the specific NOR flash chip's rated erase-cycle count** (that's a hardware datasheet fact, not something derivable from source code), and no visibility into LittleFS's actual block-reuse pattern for this specific access pattern without running it for a very long time or instrumenting the flash driver directly. Rough order-of-magnitude, stated as an assumption, not a verified fact: at ~1 checkpoint write/2s, that's ~43,000 writes/day, ~15.8M/year. Typical NOR flash is rated for 100,000+ P/E cycles per block; if LittleFS's wear-leveling amortizes these 36-byte writes across even a modest number of blocks, years of operation is plausible — but this is an **assumption chain, not a measurement**, and this audit explicitly declines to certify a specific lifetime number from it.

**Mark this section NOT PROVEN** per the mandate's own instruction ("mark it NOT PROVEN if the partition/write-amplification data is unavailable") — it is unavailable here: no flash datasheet, no LittleFS internal block-allocation trace, no multi-year soak test exists or was run.

**Checkpoint rate-limiting/coalescing:** **ABSENT** — `totalizer.service()` is called unconditionally every telemetry tick (every 1s) with no batching/coalescing logic in `totalizer.h`. This is a design choice trading flash-write frequency for minimal data-loss window (the architecture's own stated tradeoff), not an oversight, but it is the reason the "hot sector" concern above exists at all.

**Filesystem GC blocking sampling:** **NOT PROVEN** — LittleFS's internal garbage-collection/compaction behavior under this specific access pattern was not observed at runtime (no long-duration test was run), and is not something visible from the application-level source alone.

**Severity: P2** (real long-term unknown, but not an immediate blocker for a *supervised pilot* — it is a blocker for **unattended, multi-year field deployment** without a real flash-wear measurement). **Blocks plant deployment for indefinite/unattended service: Yes, pending measurement. Blocks a short, supervised pilot: No.**

## 3. Power Failure Recovery — Verdict: **PARTIAL — code-sound design, unverified under real power-cut**

Every specific timing scenario the mandate lists, traced through the actual code:

| Scenario | Code-level behavior | Proof basis |
|---|---|---|
| Power loss before row write | Nothing written yet; no loss beyond the in-RAM sample (≤1s of data) | Code-only |
| Power loss during row write | Torn write detected by CRC32 mismatch on next read, silently skipped, "next telemetry tick continues" (`queue.h:281-284`) | Code-only |
| Power loss after row write, before checkpoint | Row is already durable; `seq` regenerates identically next boot; server absorbs the resulting duplicate via `PRIMARY KEY(device_id,seq)` — **by design, confirmed in the code's own explicit ordering comment** (`covio_firmware.ino:194-197`) | Code-only |
| Power loss during checkpoint write | Torn checkpoint fails CRC; the other ping-pong slot (previous good value) is used (`totalizer.h:185-196`) | Code-only |
| Power loss after server persistence, before device receives response | Device never sees `ack_seq`; retries the same (already-inserted) rows next cycle; DB `INSERT OR IGNORE` absorbs the resend with zero duplication | Code-only |
| Power loss after response, before ack-cursor persistence | Device reboots still holding the old cursor; resends already-acked rows; server no-ops them (idempotent) | Code-only |
| Power loss during ack-cursor write | Torn write fails CRC; dual-slot fallback recovers the previous good cursor (`queue.h:459-467`) | Code-only |
| Power loss during segment pruning/deletion | Cursor is persisted **before** any segment file is deleted (`queue.h:409-414`); a crash here just re-recognizes and re-deletes the same already-acked segment next boot | Code-only |
| Brownout during a LittleFS/NVS write | Same torn-write CRC handling as above for LittleFS; NVS's own ESP-IDF-level wear-leveling/atomicity is assumed standard, not independently re-verified | Code-only, NVS internals NOT independently verified |
| Rapid repeated reboot loops | No explicit crash-loop detection or backoff exists anywhere in this codebase (confirmed by full read of `covio_firmware.ino`, `store.h`, `diagnostics.h` — no persisted reboot counter) | Code-only; **ABSENT**, not "handled" |

**What real evidence this audit actually has:** one real, unplanned reset occurred during a passive serial listen (`USB_UART_CHIP_RESET`, not a power-cut or brownout). Across it, the totalizer recovered `total=280` (up from `total=0` at the prior boot) and the queue's `acked_seq` advanced correctly (`12416`→`15581`→`15624` across the session) with no observed corruption or duplication. **This demonstrates the checkpoint/recovery mechanism functions correctly for a soft reset on real hardware — it does NOT demonstrate recovery from an actual power interruption, brownout, or a randomized-interruption test campaign, none of which this audit had the hardware (relay, controlled power supply) to perform.**

**Corrupt-row/segment/checkpoint code paths, individually verified by reading:** torn-row skip (`queue.h:281-284`), orphan-segment cleanup for an interrupted rollover (`queue.h:574-606`), checkpoint dual-slot fallback (`totalizer.h:79-87`), ack dual-slot fallback (`queue.h:96-100`) — all present and structurally sound by inspection. Filesystem mount-failure: `covio_firmware.ino:84-88` halts loudly into a serial-console-only loop rather than proceeding silently unpersisted — real, verified in code.

**Can totals diverge from durable queue contents?** No structural coupling was found that would allow this — the totalizer checkpoint and the queue's write-offset checkpoint are stored in the *same* `Checkpoint` struct (`totalizer.h:30-45`) and persisted together via the same `persist_()` call, so they cannot independently desync from a torn write (either both reflect the last good `persist_()` call, or the previous one).

**Can reboot double-count pulses?** No — the PCNT hardware register is drained into `accumulated_`/`base_` monotonically; a reboot re-reads the last-good checkpoint's `total` and continues from there. The live device's own recovered totals across the observed reset (0→280, an increase, not a jump or reset) are consistent with this.

**Severity: P1.** The design is sound by inspection and behaved correctly for the one real (soft) reset observed. **Blocks unsupervised plant deployment: Yes** — a real power-cut/brownout fault-injection campaign (the mandate's own randomized-interruption-cycle requirement) has never been run against this or any build of this firmware, on this or any hardware. This is the single most consequential untested claim in the whole audit and should not be waived for a plant install without at least a bench power-cut test campaign.

## 4. Guaranteed Delivery / Idempotency — Verdict: **PASS (effectively-once via idempotency), with one real defect**

**True delivery semantic: at-least-once transport, made effectively-once by a real DB-level idempotency constraint** — not literally exactly-once (a duplicate *delivery* can and does happen, e.g. a lost-ack resend), but a duplicate *business record* cannot land twice, because:
- Identity = `(device_id, seq)`, and `seq` is **globally monotonic across reboots** (never resets to zero on reboot — `store.h`'s own `boot_id` mechanism exists precisely so seq doesn't need to reset), confirmed in `covio_firmware.ino:101` (`seq = totalizer.lastSeq()`).
- `server.py:161`: `PRIMARY KEY (device_id, seq)` on the `records` table — a **real SQLite primary-key constraint**, not an application-level `.exists()` check. `INSERT OR IGNORE` against this constraint is atomic and race-safe at the SQLite engine level — concurrent duplicate requests cannot both succeed in inserting the same `(device_id,seq)` row.
- This directly answers "is dedup DB-enforced or app-level" — **DB-enforced**, confirmed by reading the actual `CREATE TABLE` statement, not inferred from behavior.

**End-to-end idempotency as an exactly-once substitute:** yes, for the business guarantee that matters (no duplicate reading is ever double-counted in stored data or in totals, since totals are also raw-pulse-cumulative and idempotent by the same mechanism) — **explicitly stating what is NOT guaranteed:** the *transport* can and will deliver the same batch twice under normal, expected operation (that is the whole point of "at-least-once + idempotent identity"), and this was not something requiring a special test — it's confirmed as the intended, working design, not a residual risk.

**Collision resistance across resets/reprovisioning/backups:** `seq` never resets on reboot (only `boot_id` increments) — collision-safe across reboots. Sequence wraparound: `seq` is a `uint32_t` (`covio_firmware.ino:46`, `QRow.seq` in `queue.h:56`) — wraps at ~4.29 billion. At 1 sample/sec that's ~136 years to wrap — **not a practical risk** for this device's lifetime. Device reprovisioning/`device_id` change: `device_id` is derived from the MAC address (`store.h:84-90`, `chipId()`), **immutable in practice** (there is no setter for it anywhere in `store.h`) — so a "device ID change" scenario as the mandate describes is **structurally impossible** via the documented API; the closest analogue is the separate, mutable `logical_device_id` (manufacturing serial), which has its own write-once protection at the factory-provisioning endpoint (`local_api.h:211-224`, re-verified: re-submitting the *same* value is idempotent-accepted, a *different* value once assigned is rejected with `409`). Restored backups: if a device's flash/NVS were restored from an old backup, its `seq` would resume from a *lower* value than what the server already has for `(device_id, seq)` — those older `seq`s would simply be silently ignored (`INSERT OR IGNORE` no-ops them), and its `boot_id` would collide with the same value used before the backup — **but since the DB's uniqueness key is `(device_id, seq)`, not `(device_id, boot_id, seq)`, this is safe by construction**, not merely "probably fine."

**Concurrent duplicate requests:** covered above — DB constraint makes this race-safe regardless of application-level timing.

**Real defect found (already detailed in `02_END_TO_END_DATA_FLOW.md`):** a permanently-quarantined record creates a permanent gap in the cumulative-ack contiguous scan, freezing the device's queue-pruning forever for all data after that gap, even though the server keeps successfully storing it. This is **not** a duplicate-data risk — the server-side data is fine — but it **is** a real "cumulative acknowledgement can accidentally get stuck on a gap" finding the mandate explicitly asked about. See `11_RISK_REGISTER.md` RISK-01.

**Out-of-order batches / pruning:** `pending()` always reads FIFO from the persisted cursor (`queue.h:250-299`) — a batch cannot be sent out of order by the device itself (no reordering logic exists), so this specific risk is **structurally absent** on the device side.

**Severity of the ack-gap defect: P1.** **Blocks plant deployment: Yes** for the ack-gap defect specifically — it is a real, reproducible-by-code-logic condition (not requiring hardware) that causes unbounded local storage growth under a realistic-if-uncommon trigger (a schema/field validation failure on an otherwise-healthy device, e.g. during an OTA rollout window mixing schema versions if that window is ever mishandled). The rest of Section 4 is **PASS**.

## 5. Offline Sync Engine — Verdict: **PARTIAL**

- **Pulse capture continues offline:** Yes, structurally guaranteed (PCNT hardware, independent of `Sync`/network state) — code-only but architecturally unambiguous.
- **Samples keep queuing during outage:** Yes — `covio_firmware.ino`'s telemetry-tick block (`186-198`) has no dependency on `syncEngine.online()`; it runs unconditionally every second.
- **Main loop responsiveness:** `sync.h` bounds its HTTP calls with `http.setTimeout(8000)` (push) and `.setTimeout(6000)` (config poll, OTA manifest poll) — **bounded**, confirmed by reading the actual calls, not assumed. The OTA `.bin` **download** itself (`ota.h:157-175`, via `httpUpdate.update()`) has **no visible explicit timeout override** in this code — it relies on the `HTTPUpdate`/`HTTPClient` library's own defaults, which this audit did not independently verify are bounded to a specific value. This is a real, if narrow, gap: an OTA download over a very slow or stalled connection could block longer than the push/config paths' explicit 6-8s bound. **Mark this specific sub-claim NOT PROVEN**, not "safe."
- **Retry/backoff:** real exponential backoff with jitter for WiFi reconnect (`sync.h:64-75`: doubles each attempt, capped at 120s, `+ esp_random() % 1000` jitter) — **PASS**, this is a genuinely good implementation, not just present but correctly randomized. Push/config-poll retry is fixed-interval (every `PUSH_PERIOD_MS`/`CONFIG_POLL_MS`), **not** backed off on repeated failure — every failed push is retried again in exactly 5 seconds forever, with no backoff. This is a real, if minor, gap for a genuinely-down server scenario (constant 5-second retry traffic indefinitely) but does not risk device stability.
- **Reconnection automaticity:** Yes, `wifiService()` runs unconditionally in `loop()` (`covio_firmware.ino:157`).
- **Backlog drains without starving new readings:** Yes structurally — telemetry-tick and push are two independently-timed blocks in the same loop, neither blocks the other beyond the bounded HTTP timeout above.
- **Batch ordering:** strictly FIFO from the persisted cursor — guaranteed by code structure, not merely observed.
- **Server rate-limit handling:** **ABSENT** — `server.py` has no rate-limiting middleware of any kind (confirmed by full read); there is nothing for the firmware to "handle" because the server never signals a 429 in the first place under this reference implementation. A real production receiver could add rate limiting; the firmware's `pushOnce()` would treat a `429` the same as any other non-200 (keep queue, retry next cycle) — reasonable default behavior, but never exercised.
- **Permanent failed-state risk:** no code path was found that could leave the device in an unrecoverable state from network conditions alone (every failure path returns to the normal loop) — **PASS** for this specific sub-question.
- **Realistic "several days offline" claim:** at the ~5.5-hour soft-threshold buffering figure from Section 1 (itself dependent on an unverified partition-size assumption), "several days" is **not achievable within the soft-threshold window**, though the device does **not** stop buffering at that threshold — it keeps accepting data (flagged, not blocked) until the true physical flash limit (estimated ~26h at 1/sec, unverified partition size). **"Several days" is only true if the real sampling interval in the field is much sparser than 1/sec, or if the true partition size is meaningfully larger than the ~3.4MB comment claims** — this audit cannot confirm either without a real partition-table read. Any documentation claiming "several days of offline buffering" as a flat, cadence-independent fact should be corrected or scoped to the actual assumptions.

**Severity: P2.** **Blocks plant deployment: depends entirely on the customer's actual required sampling interval and offline-duration SLA** — this must be confirmed against the real partition size before a plant commitment is made on "several days offline" language.

## 6. Queue Management — Verdict: **PARTIAL — one real defect (see Section 4/RISK-01)**

- **State model:** implicit, not an explicit pending/in-flight/acked/failed/quarantined state machine on the device. A row's state is entirely derived from its position relative to the persisted ack cursor: at-or-before cursor = acked (and eventually deleted), after cursor = pending. There is **no "in-flight" state at all** — `pending()` never marks anything as "being sent," so the same rows can be read and sent again on the very next cycle if the previous attempt's response was lost, which is intentional (this is what makes the design idempotent-safe) — but it does mean the mandate's specific state-machine vocabulary (pending/in-flight/failed/quarantined) does not literally exist on-device; it's a coarser two-state model (acked vs not) that achieves the same safety property differently.
- **Durable across reboot:** Yes — the cursor itself is a dual-slot CRC-checkpointed file, recovered at boot exactly like the totalizer.
- **Multiple sync workers racing:** **structurally impossible** — this is a single-threaded Arduino `loop()`; there is exactly one call site to `pushOnce()` (`covio_firmware.ino:203`) and no FreeRTOS task or interrupt handler ever calls it. The enterprise checklist's "can a record be selected twice by concurrent workers" concern does not apply to this architecture — stated plainly rather than inventing a race that cannot occur here.
- **Record selected twice by the *same* single worker (retry, not race):** yes, deliberately — this is the intended at-least-once behavior, made safe by the DB's idempotency constraint (Section 4).
- **Failed batches blocking later records:** a non-200 response keeps the *entire* queue untouched and retries the *same* batch next cycle (`sync.h:124-128`) — so yes, a batch that fails outright (e.g. genuine network failure, or a server 500) does block progress on everything in it until it succeeds, by design (there's no partial-success handling at the transport-failure level — only at the per-record quarantine level once the request *does* reach the server). This is reasonable for transport failures (nothing was processed) but is the exact mechanism behind the RISK-01 poison-gap defect once the request *does* reach the server and one record is rejected.
- **Poison records causing infinite retry: CONFIRMED, see RISK-01.** This is the single most important finding of this entire audit and is not a hypothetical — it follows directly and inevitably from reading `push()`'s ack-computation loop against `queue.h`'s FIFO-resend behavior.
- **Retry counts / last-errors stored:** **ABSENT** — no retry counter or last-error string is persisted anywhere on-device (confirmed across `queue.h`, `sync.h`, `store.h`).
- **Segment deletion crash-safety / can it delete unacked records:** No — verified in Section 3 (cursor persisted before deletion; deletion range is always `< seg <= activeSeg`, and the active segment, where new/unacked data may still land, is never deleted).
- **Ack-cursor monotonicity:** strictly enforced — `ackThrough()`'s very first line is `if (ackedSeq <= ack_.acked_seq) return;` (`queue.h:331`) — a stale/lower ack_seq is a structural no-op, cannot move the cursor backward.
- **Gaps in acked ranges:** by definition impossible on the device side — "acked" is a single scalar cumulative watermark (`acked_seq`), there is no concept of a non-contiguous acked set to have gaps in. (The *quarantine* gap described in RISK-01 is a different thing — a gap in what the *server* considers acceptable, not a gap in the device's own acked range.)
- **Missing/corrupt records surfaced remotely:** **partially** — the server has a `quarantined_records` table (queryable via direct DB access, no dedicated `/admin` endpoint was found exposing it as a count or list — confirmed by grepping all `@app.route` definitions in `server.py`, none serve quarantine data). On the device, a CRC-failed row is simply skipped with a Serial log line and no persisted counter — **not surfaced via any local API field** (`diagnostics.h`'s `buildMetricsJson()`/`buildStatusJson()` have no corrupt-row-count field). **ABSENT** as a remotely-visible signal on both sides.
- **The required invariant** ("every accepted sensor reading is either durably pending, durably acknowledged, or explicitly quarantined with an auditable reason") — **does NOT fully hold** for two distinct reasons found in this audit: (1) a CRC-failed row on the device is dropped with no auditable trail beyond an ephemeral Serial log line — it is neither pending, acked, nor quarantined-with-a-record, it simply vanishes from the device's own accounting (though such a row was, by definition, never durably confirmed in the first place, so this is a narrow/edge case); (2) more importantly, RISK-01 shows a row *can* be durably pending forever with no path to acked *or* quarantined-on-the-device-side (the quarantine only exists server-side; the device has no visibility that its row was quarantined at all — it just sees "ack_seq isn't advancing" with no diagnostic explaining why).

**Severity: P0** (RISK-01 alone). **Blocks plant deployment: Yes**, until RISK-01 is remediated — see `12_REMEDIATION_PLAN.md`.

## 7. Acknowledgement Mechanism — Verdict: **PASS**

Traced precisely, line by line, in `sync.h:120-142`:
- Required HTTP status: exactly `200` — anything else (`code != 200`) is treated as "keep queue, retry" (line 124).
- Content-type/schema: no `Content-Type` check at all — the code parses the body as text regardless of what content-type header (if any) the server sent. This is a real, minor robustness gap (a non-JSON `200` response, e.g. from a misconfigured proxy returning an HTML error page with a `200` status, would fall through to the `ack_seq` extraction step below).
- **`ack_seq` presence/validity check — the single most important thing to verify precisely, and it was:** `extractLong_()` (`sync.h:187-198`) returns `-1` if the key `"ack_seq"` is not found, or if it's found but no digit characters follow it. The caller (`sync.h:134-137`) explicitly checks `if (ackSeq < 0)` and treats that as **not an ack** — queue is kept, logged as `"200 but no ack_seq — keeping queue"`. **This confirms, by direct re-reading of the current file (not by trusting an earlier report's paraphrase), that a bare HTTP 200 with an empty/garbled/missing-ack_seq body does NOT prune the local queue.** This is Invariant 6, genuinely implemented as documented.
- **Ack beyond the sent range / stale-or-lower ack:** `ackThrough()`'s own first line (`queue.h:331`) rejects any `ackedSeq <= ack_.acked_seq` as a no-op — a stale/lower ack cannot move the cursor backward. An ack *beyond* what was actually sent is not separately checked (there's no comparison against "the highest seq in the batch we just sent") — but since the server can only ever compute `ack_seq` from what it has actually durably stored in `records`, and it can only have stored records the device actually sent, an "ack beyond sent range" is not really reachable through the real server logic — it would require a malicious/buggy server, which is a trust-boundary question (see Section 12), not a firmware-parsing gap.
- **Malformed JSON:** the naive parser doesn't validate JSON structure at all — it just scans for the literal substring `"ack_seq"` followed by a colon and digits, anywhere in the response body. A genuinely malformed body that happens to contain that exact substring pattern elsewhere (e.g., in an error message) could be misparsed as a valid ack. This is a **real, if low-probability, robustness gap** given the trusted/controlled server contract — worth hardening, not a functional failure today.
- **Timeout after server commit / TLS close before full body / truncated response:** all fall through to `http.POST()` returning a non-200 (or the connection erroring out before `getString()` completes) — in every such case the code path is "code != 200" or an empty/unparseable body → queue kept. **This means a real risk exists in the opposite direction of what the checklist worries about:** the server may have already durably committed the record (per its own idempotent-insert transaction), but if the response is lost, the device correctly does *not* prune — it just resends, and the DB's `INSERT OR IGNORE` absorbs the resend for free. **No local record is ever pruned merely because a transport-layer 200 was seen without a validated body** — this was directly re-verified against the current code, not assumed.

**Severity: none — this is a genuine PASS.** No remediation required for the ack mechanism itself; the minor JSON-robustness gap noted above is a P3 hardening item at most.

## 9. Firmware Updates (OTA) — Verdict: **PARTIAL — real safety mechanism present, never demonstrated on hardware**

- **Signed manifests / firmware authenticity:** **ABSENT** — the manifest (`{"version":...,"url":...}`) is fetched and trusted with no signature, and the `.bin` itself has no hash/signature check beyond whatever TLS+CA-pinning is in effect for the transport (`ota.h`'s own header comment states this plainly: "Enable Secure Boot + signed app images... NOT DONE here"). Confirmed by code: no `mbedtls` signature-verification call anywhere in `ota.h`.
- **HTTPS download:** **implemented in code**, real scheme-dispatch (`ota.h:104-114,167-175`) using `WiFiClientSecure`/`setCACert` when the URL is `https://`, falling back to plain `WiFiClient` only for `http://` (bench-only, by design). The live device is currently configured `http://`, so this specific unit is not exercising the HTTPS path today — but the capability genuinely exists in the compiled firmware (confirmed: `esp32dev` built successfully with this code path present) — this is a real distinction worth stating precisely rather than conflating "capability exists" with "this unit uses it."
- **A/B OTA partitions:** confirmed via `platformio.ini`'s `default_16MB.csv` (two app slots) and `esp_ota_ops.h` usage in `ota.h`.
- **Bootloader rollback:** genuine, standard ESP-IDF app-rollback mechanism, correctly wired: `noteBoot()` (`ota.h:70-78`) detects a pending-verify trial image at boot; `confirmHealthyBoot()` (`ota.h:83-88`) calls the real `esp_ota_mark_app_valid_cancel_rollback()` **only after** the device has both reconnected to WiFi and gotten a successful push-ack or config-poll 200 (`covio_firmware.ino:203-218`) — this is a genuinely sound gate (not just "confirm on next boot unconditionally"), confirmed by reading the actual call sites, not assumed from the class name.
- **Rollback timeout:** relies on the ESP-IDF/Arduino-core default rollback-timeout behavior — **not independently verified** in this audit (no `sdkconfig` override was found, meaning framework defaults apply, and this audit did not cross-check what that default actually is against the installed core version).
- **Compatibility/hardware-revision checks:** **ABSENT** — no model/hardware-id check exists in the manifest or `doUpdate_()`.
- **Partition/schema migration across an OTA:** the queue/totalizer's own dual-format migration logic (`totalizer.h`'s `LegacyCheckpoint` handling, `loadLegacy_()`) demonstrates the project *has* handled at least one real on-disk-format migration correctly in the past — but this is unrelated to OTA itself; LittleFS (a separate partition from the app partitions) is never touched by `HTTPUpdate`, so queue/config data is structurally preserved across an OTA regardless.
- **Insufficient-space / interrupted-download / invalid-image handling:** delegated entirely to the `HTTPUpdate` library's own internal handling — this audit did not independently stress-test any of these (would require an actual OTA attempt against real hardware, explicitly out of the agreed non-destructive scope). `doUpdate_()`'s `switch` on `HTTP_UPDATE_FAILED` (`ota.h:177-183`) correctly logs and leaves `failed_=true` without bricking the running image (the device simply stays on its current, already-running, already-confirmed-good image) — sound by inspection.
- **Wrong-device-image handling:** **ABSENT** — no model check exists before flashing.
- **Rollback reporting:** `ota.state()` exposes `pending_verify`/`confirmed`/`failed` (`ota.h:60-65`, confirmed live: the connected device currently reports `{"state":"none"}`, i.e. no OTA has ever occurred on it) — but there is **no distinct `"rolled_back"` state**; a device that silently rolled back would simply reboot back onto its prior image and report `confirmed` again (from that prior image's own earlier confirmation) or `none` — an operator watching only `ota.state` cannot distinguish "this device just successfully rolled back from a bad update" from "this device never attempted an update." **This is a real observability gap** for an operationally important event.
- **Staged/canary rollout, pause/cancel, fleet-jitter:** all **ABSENT** — `server.py`'s manifest mechanism is a single static file (`server/firmware/manifest.json`) serving one version to every device that asks; there is no per-device targeting, no rollout percentage, no pause/cancel control, and `OTA_POLL_MS` (`config.h:69`, fixed 5 minutes) has no jitter — a fleet of many devices would poll and potentially update in a near-simultaneous wave. This matches RE-9/RE-10's own disclosed scope, re-confirmed here directly against the code rather than the doc.
- **What was NOT demonstrated:** an actual successful OTA upgrade on real hardware, and an actual forced-bad-image rollback on real hardware. **Both are explicitly marked NOT PROVEN** — the mandate itself says not to mark OTA PASS merely because the mechanism exists in code, and this audit follows that instruction: the rollback *mechanism* is soundly designed and uses correct, standard ESP-IDF primitives, but it has never been exercised end-to-end on this or any physical unit in any session on record.

**Severity: P0** for plant deployment specifically because OTA rollback — "the single highest-impact unexecuted test," in RE-10's own words, independently re-confirmed here — remains completely unproven on hardware, and because Secure Boot's absence means a compromised/malicious `.bin` at a compromised URL would be accepted and flashed (mitigated only by CA-pinned HTTPS, not by artifact-level signing). **Blocks plant deployment: Yes**, until at minimum one real successful OTA and one real forced-bad-image rollback have been demonstrated on physical hardware.

## 10. Watchdog and Self-Healing — Verdict: **PARTIAL / NOT PROVEN**

- **Watchdog configuration:** **no explicit task/hardware watchdog configuration was found anywhere** in this codebase (`esp_task_wdt` does not appear in any `.h`/`.ino` file, confirmed by a repo-wide grep). The Arduino-ESP32 core does enable certain IDL-task-level watchdogs by default at the ESP-IDF layer independent of application code, but this firmware neither configures nor explicitly feeds any watchdog of its own — **this audit cannot state with confidence what would happen if `loop()` ever genuinely hung** (e.g., an unbounded library call), because the actual default watchdog behavior of this exact core/config combination was not independently tested. **Mark NOT PROVEN**, not "safe" and not "unsafe."
- **Main-loop blocking calls:** push (`8000ms`) and config-poll/OTA-manifest (`6000ms`) HTTP calls are explicitly bounded (confirmed by reading the actual `setTimeout()` calls). The OTA **binary download** itself has no explicit override found — relies on library defaults, **NOT PROVEN** bounded.
- **Deadlock possibility:** genuinely, structurally **impossible** in the classic multi-thread sense — this is a single-threaded cooperative loop with no mutexes, no second task, no ISR-driven state machine competing for a lock. The only failure mode possible here is a **long stall** (a blocking call that takes longer than expected), not a deadlock — stated precisely rather than conflating the two.
- **Heap exhaustion handling:** **ABSENT** — no `ESP.getFreeHeap()` check or low-memory response exists anywhere in the firmware's control flow (it is only *read* for reporting via `/api/v1/metrics`, never *acted on*). An actual OOM condition would presumably crash/panic and reboot via the framework's own default heap-corruption handling — not something this firmware manages proactively.
- **Filesystem mount-failure behavior:** re-verified precisely — `covio_firmware.ino:84-88`: `LittleFS.begin(true)` failing prints `[FATAL]` and enters `while(true){ provision.service(); delay(50); }` — an intentional infinite loop, **not** `ESP.restart()`, keeping the serial console alive for manual recovery rather than silently rebooting forever. This is a deliberate, sound design choice (fail loud, stay debuggable), confirmed by reading the actual code path, not assumed from a doc description.
- **Repeated crash-loop detection:** **ABSENT** — no persisted counter of any kind tracks consecutive reboots or reset reasons across boots (confirmed: `store.h`'s NVS schema has no such field, and `diagnostics.h`'s `resetReasonStr_()` only reports the *current* boot's single reset reason, real ESP-IDF `esp_reset_reason()`, exposed via `/api/v1/metrics` — genuinely implemented, just not accumulated into a history).
- **Safe-mode/recovery-mode:** **ABSENT** as a distinct concept beyond the filesystem-mount-failure halt described above.
- **Restart-reason persistence across reboots:** **ABSENT** — only the current boot's reason is computed live via `esp_reset_reason()`; nothing is written to NVS/flash to build a history.
- **Queue/totalizer restoration after reset:** genuinely proven, both by code (Section 3) and by the one real reset observed this session.
- **Automatic service resumption:** yes — `setup()` is fully self-sufficient; no manual step is required after any reset for normal operation to resume (confirmed by reading the full `setup()`/`loop()` flow, and by the real device resuming normal telemetry/sync automatically after its observed reset).
- **Remote notification of restart:** **partially** — a reboot increments `boot_id`, which is carried on every subsequent record and diagnostically visible server-side (`records.boot_id` column), but there is no explicit "device just rebooted" event pushed anywhere (no `device_events` row is ever created for a device-side reboot — only for provisioning/key/calibration events initiated server-side).

**Severity: P2.** **Blocks plant deployment:** not by itself, but combined with Section 3's unproven power-fault-injection status, the absence of any watchdog/crash-loop safety net is a real gap for **unattended** field service — a device that entered a genuine hang (not covered by the structurally-impossible-deadlock argument above, but a genuine long stall in an unbounded call) would have no independent recovery mechanism beyond whatever the ESP-IDF framework does by default, which this audit did not verify.

## 11. Time Accuracy — Verdict: **ABSENT (no wall clock on-device), and this is by design, not an oversight**

- **RTC hardware:** **ABSENT** — confirmed both by `config.h`'s own comment ("No SD card on this unit... MAX31865 removed") and by grepping the entire firmware tree for any RTC driver (`DS3231`/`PCF8563`/etc.) — none exists.
- **NTP:** **ABSENT** — confirmed by a repo-wide grep for `configTime`/`sntp_` across every `.h`/`.ino` file — zero matches. The device has **no wall-clock concept whatsoever**.
- **What is actually stamped:** `QRow.ts` is literally `now/1000` — i.e. **milliseconds-since-boot, divided down to seconds** (`covio_firmware.ino:191`, `Telemetry::build()`'s `uptimeSec` parameter) — confirmed directly in the struct comment too (`queue.h:57`: "device uptime seconds (server stamps wall-clock)"). This is boot-relative, not calendar time, and is meaningless across a reboot without a reference point.
- **Server-side wall clock:** `server.py`'s `records.recv_ms` column is populated from `int(time.time()*1000)` at the moment the server receives and processes the batch (`server.py:525,573,601`) — this is the **only** wall-clock timestamp anywhere in the entire system, and it reflects receipt time, not the moment the pulse was actually counted (which could be seconds-to-hours earlier if the device was offline and buffering).
- **Sequence-based ordering independent of wall clock:** yes, fully — `(boot_id, seq)` gives a complete, gap-free relative ordering regardless of any clock, and this is what the architecture actually relies on for correctness (idempotency, ack computation) — wall-clock time plays **no role** in any correctness-critical logic anywhere in this system.
- **Is sequence + server reconciliation an adequate substitute for real timestamping?** For the device's own internal correctness (dedup, ordering, totals) — **yes, fully adequate**, and arguably a *more* robust design than relying on a cheap/unsynced on-device clock. For **attributing a reading to the real-world moment it actually occurred** — **no, not adequate**, if that granularity matters: a batch of 50 buffered readings that all arrive in one push after an 8-hour outage will all be recorded with `recv_ms` values clustered around the *moment connectivity was restored*, not the real times (hours apart) the underlying pulses actually occurred. The device's own `ts` (uptime-seconds) *could* in principle be used server-side to back-calculate real timestamps once wall-clock is known at any single reference point per boot — **but no code anywhere does this reconstruction**; `recv_ms` is the only timestamp actually stored and displayed.
- **Business consequence:** for flow-totalizer/consumption billing purposes (where what matters is *cumulative volume over a billing period*, not the exact real-world second any individual pulse occurred), this is very likely adequate — the totalizer is monotonic and idempotent regardless of when records happen to arrive. For any requirement involving **precise event-time attribution** (e.g. "what was the flow rate at 14:32 on Tuesday" during a period the device was offline), the system as built **cannot answer that accurately** — it can only say "sometime before this batch arrived, cumulative total had reached this value."

**Severity: P2** for a flow-totalizer/billing use case (likely acceptable); **P0** if any compliance or dispute-resolution requirement needs precise historical event-time attribution during offline periods. **Blocks plant deployment:** depends entirely on the customer's actual timestamping requirement — this must be explicitly confirmed with the business owner before an install, not assumed either way.

## 12. Security — Verdict: **PARTIAL — real, working controls exist alongside real, disclosed gaps**

- **TLS usage / cert validation:** genuinely implemented — `setCACert()` used, `setInsecure()` **never** called anywhere (confirmed: the only two matches for `setInsecure` in the whole repo are in *comments* explicitly forbidding it, `sync.h:104`, `ota.h:18`). Real code, not just a doc claim.

The only way to run without TLS is the explicit `http://` scheme path, which is a *documented, deliberate* bench-only affordance (`config.h:22-27`), not a disableable-TLS bug.

- **Debug/JTAG/UART exposure:** the connected unit uses ESP32-S3's native USB-Serial/JTAG (confirmed via the real `VID_303A` USB descriptor and `platformio.ini`'s own comment) — this is a genuine physical-access attack surface (full serial console with `show`/`set key`/`factory` commands, zero authentication) but is **not remotely reachable** — correctly scoped as a physical-access risk, not a remote one.
- **Physical extraction risk:** real and current — no Secure Boot, likely no flash encryption (unverified, not disproven), full serial console access with no auth. **A determined attacker with physical possession of a device can very likely extract the API key, WiFi password, and reflash arbitrary firmware.** This matches the project's own explicitly-stated design philosophy (ADR-005: "physical possession is the trust boundary") — a reasonable, disclosed tradeoff for a bench/pilot context, a real risk for equipment installed in a less-controlled plant environment.

- **Hardcoded secrets scan:** beyond the WiFi credential already flagged, no other non-placeholder secret (private key, second password, token) was found in a manual review of every `.h`/`.ino`/`.py` file read during this audit. This is **not** an automated, exhaustive secret-scanner run across the full binary/every file in the repo — treat as a manual-review-level finding, not a certified clean bill.
- **Token rotation/revocation:** real, working, server-side (`server.py`'s `/admin/devices/<id>/rotate-key`, `/revoke-key`, both confirmed against real passing tests in `test_dm_phase_4_registry.py`).
- **Per-device credentials:** the mechanism exists and works (`POST /admin/devices/provision` mints a unique key per device) — but the **live connected device has never been through it** (`api_key_status: "default"`, confirmed live) — so today, this specific unit shares the same bootstrap key as every other never-provisioned bench device.
- **API rate limiting / brute-force protection:** **ABSENT**, confirmed by a full read of `server.py` — no rate-limiting library, decorator, or manual counter exists anywhere.
- **Admin endpoint authorization:** **ABSENT** — `/admin/kfactor`, `/admin/devices/provision`, `/admin/devices/<id>/revoke-key`, `/rotate-key` all have **zero authentication**, confirmed by reading every route definition — anyone who can reach the server's port can revoke any device's key, mint new provisioning keys, or change the billing-relevant K-factor. This is explicitly disclosed by the project itself (ADR-016, "bench/pilot-scope limitation") — real and current, not a new discovery, but re-confirmed directly in code rather than taken on faith from the doc.
- **Factory-reset authorization:** **ABSENT** — the serial `factory` command (`provision.h:69-71`) requires no authentication beyond physical USB access.
- **Audit logging:** real and reasonably thorough server-side (`device_events` table — `DEVICE_PROVISIONED`, `KEY_REVOKED`, `KEY_ROTATED`, `CALIBRATION_CHANGED`, `API_AUTH_FAILED` all genuinely recorded, confirmed in code and exercised by real passing tests) — but **no on-device audit trail exists at all** for config/factory-reset/serial-console actions.

**Three-tier summary, as the mandate requires:**
- **Protected against remote attackers:** Reasonably, for the transport layer (real TLS+CA-pinning capability, real device-facing auth on push/config/OTA-manifest) — but **not** for the unauthenticated admin endpoints, which are a real remote-attacker risk if that server port is reachable from anywhere untrusted.
- **Protected against casual physical access:** No — full unauthenticated serial console, masked-but-not-secret-free local API, open provisioning AP.

**Severity: P0** (the admin-endpoint auth gap and the live hardcoded WiFi credential both independently qualify). **Blocks plant deployment: Yes**, until at minimum: (1) the live WiFi credential is rotated and removed from source, (2) admin endpoints are placed behind real authentication or a genuinely isolated management network before any plant install, (3) a decision is made and documented on whether the physical-extraction risk profile is acceptable for the specific plant environment.

**Severity: P2.** **Blocks plant deployment:** not alone, but combined with the "last error"/"retry count"/"corrupt-record count" absences, a plant operator's ability to diagnose a struggling device remotely is meaningfully limited — worth remediating before a large unsupervised fleet, less critical for one supervised pilot unit.

## 14. Factory Reset and Recovery — Verdict: **PARTIAL**

- **Trigger:** serial `factory` command only (`provision.h:69-71`) — **no remote/API path exists** for a factory reset (confirmed: no such route in `local_api.h`).
- **Authorization required:** **none** — any process with USB/serial access can send `factory` and it executes immediately.
- **Accidental-trigger prevention:** **none** — no confirmation step; the command executes on the very next newline (`provision.h:33-37,69-71`).
- **What gets cleared, verified field-by-field against `store.h`'s actual `factoryReset()` (`p_.clear()`, wiping the entire NVS namespace):** WiFi creds — cleared. API key — cleared. Device identity (`device_id`) — **not affected** (it's derived from MAC, not stored in NVS at all — `store.h:84-90`). `logical_device_id` — cleared (stored in NVS, `store.h:54-55`). Calibration cache (`kfactor`/`density`/`tref`) — cleared. **The EventQueue (LittleFS `/queue/*`) and Totalizer checkpoint (LittleFS `/totA.bin`/`/totB.bin`) are NOT touched by `factoryReset()` at all** — they live entirely outside NVS, and `provision.h`'s `factory` command never calls any `EventQueue`/`Totalizer` method. **This is a genuinely good property, verified by code, not assumed**: a factory reset preserves all unsynced measurement data and the lifetime totalizer, clearing only identity/network/calibration-cache config.
- **Health/restart history:** N/A — none exists to clear (Section 10).
- **OTA state:** not persisted across boots at all (RAM-only `pendingVerify_`/`confirmed_`/`failed_` in `Ota`), so a factory reset has no OTA-state to clear.
- **Distinct "configuration reset" vs "secure erase":** **ABSENT** — there is exactly one `factory` command, an all-NVS wipe; no finer-grained or more-thorough (secure-erase-the-flash) option exists.
- **Reset while unsynced data exists — blocked, warned, or silently allowed:** **silently allowed**, and moreover **harmless to the unsynced data specifically** since (per above) the queue/totalizer are untouched by this command — the risk the mandate is probably worried about (losing unsynced readings on reset) does **not** actually materialize here, a genuinely positive finding worth stating plainly rather than assuming the worst.
- **Remote reprovisioning wrong-identity risk:** `POST /admin/devices/provision` (`server.py:688-739`) takes a bare `device_id` string with no validation against any known-device list or confirmation step — an operator typo could provision a key intended for one physical unit against a different (or nonexistent) `device_id` string with no error, since the endpoint will happily create a new registry row for any `device_id` it hasn't seen before. **Real risk, confirmed in code**, not hypothetical.
- **Lost/stolen device revocation:** confirmed real and working (`/admin/devices/<id>/revoke-key`, tested).
- **Reset/reprovision auditing:** provisioning **is** audited (`DEVICE_PROVISIONED` event). A device-side `factory` command is **not** audited anywhere — the server has no way to know a factory reset ever happened on a given unit; it would simply reappear, indistinguishable from a first-time device, using the shared bootstrap key again until re-provisioned. **This is a real asset-tracking gap** — a stolen-then-recovered-then-reset device and a genuinely-new device look identical to the backend.

**Severity: P1** (unauthenticated physical factory reset + no reset-event audit trail). **Blocks plant deployment: Yes** for any customer requirement around asset-tracking/tamper-evidence; **No** for the specific worry about losing unsynced measurement data on a factory reset, which this audit found does not actually occur.
