# 05 — Device/Server Reconciliation (Phase 4 + Phase 5)

## Honest scope statement

The mandate's reconciliation template (pulses generated → counted → accepted → durable rows → attempted → API-accepted → DB-committed → acknowledged → pruned → final pending) requires a **controlled pulse-generation test campaign** to populate meaningfully. No pulse generator exists in this environment, and the live device's real pulses are coming from whatever sensor/simulation is actually wired to it in the field right now (unknown source, not generated by this audit) — fabricating a reconciliation table with invented pulse/record counts would be exactly the kind of manufactured evidence the mandate explicitly forbids. What follows is the **real reconciliation of the one real event this session actually observed**, plus a code-level explanation of why the general mechanism is sound.

## Why the general mechanism reconciles by construction (code-level argument, not a substitute for a real test campaign)

- **Pulses → totalizer:** the PCNT hardware register counts independently of firmware execution state; `total()` is a monotonic function of the persisted checkpoint plus whatever the hardware has counted since. Barring an actual PCNT hardware fault (not something software can induce or observe), pulses cannot be lost between the sensor edge and the totalizer's accounting — this is the architecture's own stated purpose for using PCNT instead of interrupt-counting.
- **Totalizer → durable rows:** every telemetry tick writes exactly one row per second reflecting the totalizer's value at that instant; a torn write is detected and skipped (not silently miscounted), and the *next* tick's row still reflects the correct, undiminished totalizer value — so a lost row does not lose totalizer accuracy, only that one second's granularity of history.
- **Durable rows → DB-committed:** the DB's `PRIMARY KEY(device_id,seq)` constraint plus the device's guaranteed-monotonic `seq` means every row that is ever durably written will, given enough retries, eventually be committed exactly once server-side, regardless of how many times it's resent.
- **The one place this chain is NOT closed, found by this audit:** a row that reaches the server but is *quarantined* (schema/field validation failure) is durably stored (in `quarantined_records`, not lost) but creates a permanent gap in the *device's own* view of what's been acknowledged (RISK-01) — so the reconciliation `unique device sequences generated = unique server sequences stored (records) + still-pending + quarantined` **would show a real, permanent discrepancy** in exactly this scenario: the device would believe those sequences are still "pending" forever, while the server correctly shows them as "quarantined." **This is not a hypothetical entry in this table — it is a real, code-proven failure of the reconciliation invariant the mandate asks for**, and is the single most important finding to carry into any real fault-injection reconciliation test the business subsequently runs.

## What a real reconciliation campaign still needs (not performed here)

1. A controlled pulse source (bench pulse generator or a documented, safe SIM_PULSES bench build) to generate a known, exact pulse count.
2. A test database (not the live bench `server/covio.db`) to avoid contaminating whatever real data is already in it from the live connected device.
3. A sequence of deliberate faults (server stop/restart, WiFi drop, forced quarantine via a deliberately malformed record) with before/after row counts captured at each step.
4. Repetition across enough cycles to be statistically meaningful, per the mandate's own instruction.

None of this was performed in this audit; it is recommended as the concrete next step before any unattended field deployment (see `12_REMEDIATION_PLAN.md` and `13_PLANT_INSTALLATION_RUNBOOK.md`).
