# 11 — Risk Register

| Risk ID | Severity | Component | Failure Mode | Business Impact | Evidence | Required Fix | Blocks Deployment |
|---|---|---|---|---|---|---|---|
| RISK-01 | **P0** | `server.py` `push()` ack computation + `queue.h` FIFO resend | A single permanently-quarantined record (schema/field validation failure) creates a permanent gap in the cumulative-ack contiguous scan; the device's local queue for all data after that gap can never be pruned, even though the server successfully and durably stores it | Unbounded local storage growth on an affected device; eventually hits the silent-write-failure condition (RISK-03) at true flash capacity; no operator-visible symptom distinguishes this from an ordinary connectivity outage (see RISK-06) | `server.py:531-569,614-627` vs `queue.h:250-299,329-415`; code-proven, not hardware-dependent — see `02_END_TO_END_DATA_FLOW.md` | Change the ack computation to either (a) allow the cumulative watermark to advance past a record the server has explicitly and permanently rejected (distinct from "not yet received"), or (b) give the device a way to learn a specific `seq` was quarantined (not just silently never-acked) so it can locally give up on/flag that one row instead of blocking everything after it forever | **Yes** |
| RISK-02 | **P0** | `config.h:37-38` | A real, non-placeholder WiFi password is hardcoded in source and confirmed in active use on the physically connected device | Credential compromise the moment this source is shared/reviewed by anyone outside the trusted circle; the real network this credential belongs to is exposed | Directly confirmed via live serial log + WiFi connection this session; value not reproduced in this report | Rotate the real WiFi password on the affected access point immediately; replace the hardcoded value in `config.h` with an obvious placeholder; document that AP-mode provisioning (`wifi_provision.h`, already implemented) is the intended first-boot configuration path | **Yes** |
| RISK-03 | **P0** | `server.py` `/admin/*` routes | Zero authentication on `/admin/kfactor`, `/admin/devices/provision`, `/revoke-key`, `/rotate-key` | Anyone reaching the server port can revoke devices, mint keys, or change billing-relevant K-factor | `server.py`, every `@app.route` under `/admin/` read directly, none check any credential; disclosed by the project's own ADR-016 | Add real operator/admin authentication before this server (or its production successor) is reachable from anything beyond a fully trusted, access-controlled network | **Yes** |
| RISK-04 | **P0** | `queue.h::append()` | At true LittleFS-partition-full capacity, a failed write is logged but the specific row is silently lost with no distinct alarm; totalizer keeps counting but that one second's history is gone | Silent, undetected data loss under a real, plausible operating condition (device offline long enough to fill flash) | `queue.h:137-138,183-206`; `diagnostics.h` has no corrupt/failed-write counter field | Add a persisted, remotely-visible failed-write counter and/or alarm distinct from the existing `QUEUE_HIGH`/`QUEUE_CRITICAL` soft-threshold flags | **Yes** |
| RISK-05 | **P0** | OTA rollback path | The rollback mechanism (`esp_ota_mark_app_valid_cancel_rollback()`, correctly gated) has never been exercised with a real bad image on real hardware, on this or any prior recorded session | If the mechanism does not actually work as designed, a bad OTA could permanently brick a fielded device with no recovery path | `ota.h:83-88`; RE-10's own prior audit independently flagged this as "the single highest-impact unexecuted test" | Perform a real forced-bad-image OTA + rollback test on a bench unit before any plant install where OTA will ever be used | **Yes** |
| RISK-06 | P1 | `diagnostics.h` | No "last error," retry count, or quarantined-record count is exposed via the local API or Device Manager | RISK-01's symptom (stuck queue) is indistinguishable from an ordinary connectivity outage to a remote operator | `diagnostics.h` field-by-field read, `03_ENTERPRISE_CHECKLIST_15_SECTIONS.md` §13 | Add these fields to `/api/v1/metrics` and the server-side device twin | P1 |
| RISK-07 | P1 | `server.py` dashboard (`/`) | K-factor changes retroactively recalculate all historical consumption display using the current K, not each record's own stored `kfactor_version` | Billing/compliance-relevant historical figures can silently change after a calibration edit | `server.py:944-951` vs the per-record `kfactor_version` column that is stored but unused in this view | Recompute the dashboard's litres using each record's own `kfactor_version`-matched calibration value, or explicitly document that the current dashboard is a simplified bench view not meant for billing | P1, blocks deployment **only if K-factor will be adjusted post-install in a billing-relevant way** |
| RISK-08 | P1 | Serial console (`provision.h`) + factory reset | No authentication on `factory`, `set key`, `set wifi`, `set url`; a factory reset event is never audited server-side | Physical-access tampering is possible and untraceable; a stolen/reset device is indistinguishable from a brand-new one to the backend | `provision.h:69-71`; no corresponding server-side event for a device-initiated reset | Require physical possession + explicit customer sign-off on this risk for the specific plant environment; consider a device-side "I was just factory-reset" one-shot announcement to the server on next successful push | P1 |
| RISK-09 | P1 | `local_api.h`/`wifi_provision.h` config-write endpoints | No replay protection on any config-write or admin request | A captured request (e.g. from network access during provisioning) could be replayed later | Confirmed absent by code read | Add a nonce/timestamp or move to authenticated, TLS-protected admin channels | P1 |
| RISK-10 | P2 | LittleFS wear (totalizer checkpoint) | Checkpoint file rewritten roughly every 2 seconds forever; real flash-chip erase-cycle rating and LittleFS's actual wear-leveling behavior for this pattern are both unverified | Possible premature flash wear-out over a multi-year unattended deployment; magnitude genuinely unknown (see `06_FLASH_LIFETIME_ANALYSIS.md`) | `totalizer.h:114-126,228-239`; no datasheet or long-duration measurement available | Identify the real flash part and its rated endurance; consider a real accelerated-wear measurement before committing to unattended multi-year service | P2, blocks **unattended long-term** deployment, not a short supervised pilot |
| RISK-11 | P2 | No RTC/NTP anywhere | Device timestamps are boot-relative only; wall-clock is entirely server-assigned at receipt time, not reconstructible to real event-time for data buffered during an outage | Adequate for cumulative totalizer/billing use; inadequate for any requirement needing precise historical event-time attribution during offline periods | Confirmed absent by repo-wide grep for `configTime`/`sntp_`/RTC drivers; `queue.h:57` | Confirm with the business owner whether precise offline event-time attribution is actually required; if so, this is a design gap requiring an RTC or NTP-on-reconnect implementation | P2/P0 depending on the actual business requirement — **must be explicitly confirmed before install, not assumed** |
| RISK-12 | P2 | Watchdog / crash-loop detection | No task watchdog explicitly configured; no persisted restart/brownout/watchdog-reset counters; no crash-loop detection or safe-mode exists | A device stuck in a slow hang or reboot loop has no independent recovery mechanism beyond ESP-IDF framework defaults (unverified) and no way for an operator to see the pattern remotely | `03_ENTERPRISE_CHECKLIST_15_SECTIONS.md` §10, confirmed absent by full code read | Add explicit task-watchdog configuration and a persisted restart-reason/count history | P2 |
| RISK-13 | P3 | `sync.h::extractLong_()` | Naive substring-based ack_seq parser has no real JSON validation; a response body containing the literal substring "ack_seq" elsewhere (e.g. in an unrelated error message) could theoretically be misparsed | Low probability given the trusted, controlled server contract; would need a genuinely malformed/unexpected response body to occur | `sync.h:187-198` | Consider a minimal real JSON parse for this one field, or at minimum bound the response body's expected shape more strictly | P3, does not block deployment |
| RISK-14 | P3 | No jitter on `OTA_POLL_MS`/no staged rollout | A fleet of many devices could poll and update in a near-simultaneous wave | Operational risk only at fleet scale, not applicable to a single-unit pilot | `config.h:69`, `server.py`'s single-static-manifest mechanism | Add polling jitter and per-device/staged manifest targeting before fleet-scale rollout | P3 for a single-unit pilot; P1 before fleet scale |
