## 2. SD Library Capability Review

**Investigation performed (repository only, no hardware access, no external documentation fetch):**

- Every SD-related include in the firmware is `#include <SD.h>` (`covio_firmware.ino:19`, `queue.h:21`, `totalizer.h:20`, and their `src/` duplicates) — the Arduino core's standard `SD` library, not a directly-vendored SdFat or any other library included by source in this repository.
- `README.md:29` and `IMPLEMENTATION_AND_TESTING.md:9` confirm the toolchain is **Arduino IDE with the ESP32 board package installed via Boards Manager** ("esp32 by Espressif") — i.e., the `arduino-esp32` core. This core's `SD` library is itself a thin wrapper around **SdFat** (Bill Greiman's library), which is what actually implements the FAT filesystem and the `File` object's methods.
- **No version is pinned anywhere in this repository** — no `platformio.ini`, no `library.properties`, no `VERSIONS.md`, no lockfile of any kind names an `arduino-esp32` core version or an SdFat version. `IMPLEMENTATION_AND_TESTING.md:187` even calls out, in a different context (OTA rollback), that behavior "depends on the bootloader config baked into your Arduino core build" and varies by "core version" — confirming the project is already aware its toolchain is unpinned and behavior-sensitive to that fact.
- **Existing truncate-related precedent found in the repository is insufficient for ADR-003's needs.** `totalizer.h:132` (and its `src/` duplicate) contains the only prior use of truncation-adjacent behavior in this codebase: `File f = SD.open(path, FILE_WRITE); // FILE_WRITE truncates+rewrites this slot`. This is **truncate-to-zero-on-open** (the file is reset to empty and rewritten from scratch) — a categorically different operation from ADR-003's requirement, which is **truncate-to-an-arbitrary-nonzero-offset** (shrink a file that already has content, keeping a known-good prefix and discarding only the tail). The former is universally supported by essentially any file API; the latter requires a specific `truncate(offset)`-style method, and its presence cannot be inferred from the former.
- No test file, comment, commit, or note anywhere in the repository records ever having called a truncate-to-offset API, successfully or otherwise.

**Direct answers to the five questions posed:**

1. **Which SD library is actually being used?** The Arduino `SD` library as shipped with the `arduino-esp32` core (Boards Manager package "esp32 by Espressif"), which wraps SdFat underneath. The exact version is not pinned or recorded anywhere in this repository.
2. **Which filesystem implementation is in use?** SdFat-based FAT/FAT32 access on the SD card, via the `arduino-esp32` core's `SD`/`File` wrapper classes — not LittleFS, not a raw block-device implementation, and not (per ADR-003's own "Alternatives Rejected" section) any journaling filesystem, which was deliberately rejected.
3. **Whether truncate-to-offset is already available:** **Cannot be confirmed from this repository.** The Arduino `SD` library's `File` class has, across different `arduino-esp32` core versions, sometimes exposed a `truncate(uint32_t size)` method (inherited from or delegating to SdFat's own `truncate()`) and sometimes not, depending on which core version and which underlying `File`/`FsFile` implementation is compiled in. Without a pinned core version, this cannot be resolved by reading source in this repository — it is not present here to read.
4. **Whether the repository already contains helper functions that could support this:** **No.** The only truncation-adjacent code (`totalizer.h:132`) implements a different, insufficient operation (truncate-to-zero via re-open), and no other helper, wrapper, or abstraction over `truncate` exists anywhere in `queue.h`, `totalizer.h`, or elsewhere.
5. **Whether Phase 0 was expected to validate this:** **Yes, explicitly and specifically.** The Master Plan's Phase 0 card states this as a named deliverable: *"Verify the SD/SdFat library's file-truncate capability... against the toolchain version selected for this project. Record the finding either way"* (line 275), backed by an explicit practicality flag on the ADR-003 card itself: *"This must be verified against the exact pinned library version (Phase 0) before any code is written. If a truncate-to-offset capability is not available, implementation must stop and an Architecture Change Request must be raised against ADR-003"* (line 77). Phase 0 was never completed (confirmed independently in the Phase 1 certification review) — this specific finding does not exist anywhere in this repository.

**Conclusion:** this cannot be confirmed from the repository alone. **Hardware and/or `arduino-esp32`/SdFat documentation verification against the exact pinned core version is required** before any code implementing §1's truncate-before-append requirement is written. This is Task P2-T0 in the Design Report and remains the single largest open blocker for Phase 2 as a whole.

## 3. Corrupted Checkpoint Review

**The scenario:** both dual-slot copies of the write-offset checkpoint (the extended `totalizer.h` `Checkpoint`, §1 above) fail CRC validation simultaneously — total, unrecoverable loss of the "last known good write offset" record itself (as distinct from an ordinary single-slot torn write, which the dual-slot mechanism already handles correctly by falling back to the other slot).

**Why zero-offset recovery would violate ADR-003's stated guarantee:** ADR-003's Definition of Done states, without qualification to any specific failure sub-case: *"a power-cut-during-append bench test confirms no more than the single most-recent unconfirmed row is ever lost."* The zero-initialization fallback — the pattern already used everywhere else in this codebase for "no valid checkpoint found" (e.g. `queue.h:78`, `totalizer.h:49`) — would, if applied here, set `q_offset = 0` for the active segment. Under the truncate-before-append rule (§1 above, working exactly as designed), the very next `append()` call would then see the segment's actual file size as greater than the (now-zero) checkpoint offset, and would truncate that segment to zero bytes before writing — discarding **every row in that segment**, up to `QUEUE_SEGMENT_ROWS` (10,000) rows, not just the single most recent one. This is not a bug in the truncate-before-append mechanism itself (which is behaving exactly as specified); it is a consequence of feeding it a checkpoint value (`0`) that does not actually reflect "the last known good write offset," because that value was never actually known — it was invented by the fallback, not recovered from anything.

**Worst-case data loss:** up to one full segment's worth of rows (10,000, the configured cap) — several orders of magnitude beyond the ADR's stated "single most-recent unconfirmed row" bound.

**Expected recovery behaviour:** **Not defined.** This report does not invent one. ADR-003's text describes the normal-operation mechanism (compare file size to persisted offset, truncate if larger) but says nothing about what to do when no persisted offset can be recovered at all — a state qualitatively different from "the persisted offset is available and valid, and the file happens to be longer than it." The ADR is silent, not wrong, on this specific case.

**Whether ADR-003 already defines recovery:** **No.** Confirmed by re-reading the ADR-003 section in full (lines 84–123) — the Architecture Decision, Reasoning, Alternatives Rejected, Trade-offs, Migration Strategy, and Definition of Done sections make no mention of the double-slot-checkpoint-loss case. The Master Plan's ADR-003 Implementation Card (lines 63–77) is likewise silent on it. This is a genuine gap, not a disagreement between documents.

**Whether an ACR is actually required:** **Yes.** This is not a case of "the ADR's stated mechanism turns out to be impractical" (the usual ACR trigger) — it is a case where implementing the ADR's stated mechanism exactly as written, combined with this codebase's own established fallback precedent, produces an outcome that contradicts the same ADR's own explicit correctness bound. Per Governance Rule 1 (*"Never redesign a frozen ADR... If it turns out to be wrong, you write an ACR"*) and the ACR Workflow's approval clause (*"an ACR requires the same review rigor as the original ADR"*), whichever specific recovery behavior is chosen here materially affects whether ADR-003's headline data-loss guarantee holds in a real (if rare) failure mode — this is exactly the class of decision an implementer is not authorized to make unilaterally. **This report identifies the need for an ACR and does not raise one, per instruction.** The ACR, when raised, should resolve narrowly: what should happen when the write-offset checkpoint is totally unrecoverable — candidates already surfaced in the Design Report (§4.5/§7#6) for the ACR author's consideration, not as a pre-decided answer: (a) trust the existing file size as ground truth instead of assuming zero, accepting a small risk of retaining a possibly-torn tail in exchange for not guaranteeing a full segment's loss; (b) accept the zero-init/full-segment-loss outcome explicitly, as a documented, bounded exception to the general guarantee, on the reasoning that double-slot simultaneous corruption is itself an extremely low-probability event. Neither is adopted here.

## 4. AckRec Migration Review

**Current format:** `AckRec`, 20 bytes packed — `magic`(4) + `acked_seq`(4) + `boot_id`(4) + `writes`(4) + `crc32`(4).

**Future format (Phase 2, per Design Report §3.1):** `AckRec` extended to 28 bytes packed — the same five fields, plus `cursor_segment`(4) + `cursor_offset`(4) inserted before `crc32` (so the CRC continues to cover the whole struct as before).

**Upgrade path:** `EventQueue::begin()`'s existing `loadAck_()` rejects any file whose size does not exactly equal `sizeof(AckRec)` (`queue.h:142`, an equality check, not a minimum-size check — this logic is unchanged by Phase 2). On first boot of Phase 2 firmware, the pre-existing 20-byte `ackA.bin`/`ackB.bin` files fail this check and are treated as invalid, falling through to the existing zero-initialization branch: `ack_.acked_seq` resets to `0`, and (by extension) `cursor_segment`/`cursor_offset` start at `0`.

**Why the mandatory queue drain makes this migration safe:** the forced full-drain precondition (ADR-003's own Migration Strategy, restated identically to ADR-001's) guarantees that at the moment of upgrade, `log.bin` has already been deleted by the pre-Phase-2 firmware's own all-or-nothing compaction (`maybeCompact_()`, only triggers when the queue is provably empty) — there is no historical unacknowledged data anywhere on the card for an incorrect ack floor to mismanage. A reset `acked_seq = 0` combined with a freshly-empty segment set (no `seg_*.bin` files exist yet either — they are created lazily by the first post-upgrade `append()`) means the device simply begins accumulating and sending new data as if from a clean slate; the very next successful push receives a fresh, correct `ack_seq` computed independently by the server from its own `records` table (not derived from anything the device previously reported), so no incorrect assumption on the device's part survives past the first successful push cycle.

**Whether any hidden assumptions remain:** **One**, surfaced during the Design Report and reconfirmed here: this entire safety argument depends **entirely** on the drain precondition actually having been honored operationally, for every device that gets this OTA. If an operator (in violation of the documented procedure) flashes Phase 2 firmware onto a device with a non-empty pre-Phase-2 queue: (a) the abandoned `log.bin` is never deleted (new firmware has no code path that reads or removes it — it only ever looks at `seg_*.bin`), silently stranding that data on the card forever; (b) the reset `acked_seq = 0` gives no error signal that anything is amiss — the device would appear to boot and operate completely normally. **This is not a code defect to fix** (the drain-first requirement is the architecturally correct migration strategy, matching ADR-001's identical precedent) — it is an **operational safeguard that must be enforced procedurally** (the empty-queue verification step, Design Report §4.2) and should be captured explicitly wherever the field rollout runbook for the combined Phase 1+2 OTA lives, since neither ADR-003 nor the Master Plan's Migration Checklist currently states this specific `AckRec`-format consequence in writing (see §5 below — classified there as a documentation gap, not an architectural one). No ACR is warranted for this item: the mechanism is correct as designed, and the residual risk is a process-discipline matter already covered in principle by the existing drain-first migration rule, not a new architectural decision.

## 7. Final Recommendation

## **C) One or more ACRs must be raised before implementation.**

Specifically, two distinct gating items, of two different kinds — precision matters here because they resolve differently:

1. **SD truncate-to-offset capability (§2).** This is a **verification** item, not automatically an ACR. Per the ADR's own explicit instruction, an ACR against ADR-003 is required **only if** the verification comes back negative (truncate-to-offset is unavailable on the pinned toolchain). Until that verification is performed, this item independently blocks all of §1's truncate-dependent requirements (queue redesign, segment rotation as implemented inside `append()`) — Phase 2 cannot proceed past this without either a positive finding or an ACR.
2. **Corrupted write-offset checkpoint recovery behavior (§3).** This **does** require an ACR outright, regardless of any hardware finding — it is a pure architecture-decision gap in ADR-003's text (not a capability question), and the choice of recovery behavior materially affects whether the ADR's own stated correctness bound holds. This blocks the recovery-logic component of Phase 2 specifically.

Both items must be closed — the first by verification (with a conditional ACR), the second by an ACR unconditionally — before implementation of the components they gate. Per `MASTER_GOVERNANCE.md` §8: *"No phase may be marked complete while it has an open ACR against any ADR it depends on"* — and by the same logic applied prospectively, implementation of the gated components should not *begin* while these are open either, since Rule 1 forbids implementing a guessed answer to a question the frozen architecture does not itself answer.

This report does not raise either ACR, per instruction — it identifies precisely that they are needed and precisely what each must resolve (§2's conclusion; §3's "Expected recovery behaviour" paragraph).

## 8. Implementation Authorization

**Not applicable — the recommendation is C, not A.**

Per instruction, implementation must remain blocked, and no implementation sequence, first task, expected files, expected commit title, or expected verification is produced here. Exact reasons implementation must remain blocked:

- The truncate-before-append mechanism — the foundation every other Phase 2 mechanism in `queue.h` is built on top of (§1) — cannot be implemented against an unverified assumption about the SD library's capabilities, per the ADR's own explicit stop condition (§2's concluding paragraph, quoting the ADR/Master Plan directly).
- The corrupted-checkpoint recovery path is a real, reachable code path in the design (it is not a hypothetical) whose behavior is currently undefined by the frozen architecture; writing any specific behavior for it without the ACR would be exactly the "quietly implement something smarter and call it a bug fix" pattern `MASTER_GOVERNANCE.md` Rule 1 exists to prevent.
- Several other components (segment rotation, adaptive push, `AckRec`) are individually unblocked from a pure-design standpoint (§6), but since they are implemented as part of the same functions/files as the two blocked items (`append()` contains both the truncate check and the rollover logic; the overall Phase 2 OTA is delivered as one combined release per the Migration Checklist), partial implementation ahead of the two resolutions above would not produce a coherently testable or shippable increment.

**Once both items in §7 are closed** (verification/ACR for truncate capability; ACR for corrupted-checkpoint recovery), a follow-up Implementation Authorization can be produced directly from the Design Report's existing §9 task breakdown (P2-T0 through P2-T13), updated only to reflect whatever the resolved ACR(s) specify for the recovery-logic component — no other part of the Design Report requires rework as a result of this review.
